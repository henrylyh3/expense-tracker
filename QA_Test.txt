# Senior QA Engineer — Comprehensive Flutter Expense Tracker Audit

## 1. Your Role

Act as a **Senior QA Automation Engineer, Flutter Architect, Financial Software Tester, and Security Reviewer**.

Your task is to perform an exhaustive, evidence-based quality assurance audit of my Flutter expense tracker application.

This is a real application QA task, **not a request for a generic testing checklist**.

You must inspect the actual source code, understand the current implementation, run available tests, identify defects, and determine whether the application satisfies its functional and technical requirements.

**Primary objectives:**

1. Validate that every implemented feature works correctly.
2. Detect functional bugs, financial calculation errors, data integrity problems, security risks, and architectural defects.
3. Validate all transaction, category, and currency CRUD operations.
4. Verify that the application operates completely offline.
5. Validate SQLite persistence, migrations, and database integrity.
6. Verify financial calculation accuracy across multiple currencies.
7. Validate backup and restore, including failure recovery.
8. Test edge cases, invalid inputs, and unexpected user behavior.
9. Verify UI/UX correctness on Android and iOS.
10. Produce a comprehensive QA report with reproducible findings.

**Do not assume a feature works simply because its source code exists. Verify its behavior.**

Do not claim a test passed unless it was actually executed and passed. Clearly distinguish code-review findings, automated test results, manual verification, and untested scenarios.

Do not modify production code unless I explicitly request fixes. You may create non-destructive test scripts or test files, but clearly identify any files changed.

# 5. Financial Accuracy QA — Highest Priority

This module is **CRITICAL**.

All currency calculations must use precise decimal arithmetic.

Never use floating-point arithmetic for financial values where it could introduce rounding errors.

## Required Monetary Storage Rules

Examples:

| User input | Currency | Minor units |
|---|---|---:|
| 12.50 | MYR | 1250 |
| 12.50 | USD | 1250 |
| 500 | JPY | 500 |
| 15000 | KRW | 15000 |
| 1.250 | KWD | 1250 |
| 0.01 | MYR | 1 |

Currency decimal precision must be respected.

## Mandatory Currency Conversion Tests

Use these exact test values. They are **test fixtures**, not claims about live market exchange rates.

| ID | Original | Rate to MYR | Expected MYR |
|---|---|---|---|
| FX-001 | MYR 12.50 | 1 | RM 12.50 |
| FX-002 | USD 12.50 | 4.50 | RM 56.25 |
| FX-003 | USD 10.00 | 4.70 | RM 47.00 |
| FX-004 | JPY 500 | 0.0300 | RM 15.00 |
| FX-005 | KRW 15000 | 0.0035 | RM 52.50 |
| FX-006 | SGD 25.50 | 3.40 | RM 86.70 |
| FX-007 | KWD 1.250 | 14.25 | RM 17.81 |
| FX-008 | USD 0.01 | 4.50 | RM 0.05 |
| FX-009 | JPY 1 | 0.015 | RM 0.02 |
| FX-010 | MYR 0.01 | 1 | RM 0.01 |

For these tests, use **decimal ROUND_HALF_UP** when converting a calculated MYR amount to its two-decimal minor-unit representation. If the implementation uses a different explicit rounding policy, identify the difference and evaluate consistency before deciding whether it is a defect.

## Mathematical Validation

For a transaction:

```text
original_amount =
    amount_minor / 10^currency_decimal_places

MYR_amount =
    original_amount × exchange_rate_to_MYR

amount_myr_minor =
    ROUND_HALF_UP(MYR_amount × 100)
```

Ensure the implementation does not prematurely round the exchange rate or original amount.

## Exchange Rate Snapshot Test

1. Configure USD at 4.50 MYR.
2. Create a USD 10.00 expense.
3. Verify the saved MYR amount is RM 45.00.
4. Change the default USD rate to 4.70.
5. Reopen the original transaction.
6. Verify its snapshot remains 4.50.
7. Verify its stored MYR amount remains RM 45.00.
8. Create another USD 10.00 expense.
9. Verify the new transaction uses 4.70 and stores RM 47.00.
10. Verify total expenses equal RM 92.00.

Changing the default currency rate must **never recalculate existing transactions automatically**.

## Additional Financial Tests

Validate:

- Positive and negative net cash flow
- Income versus expense aggregation
- Decimal precision for zero-, two-, and three-decimal currencies
- Rounding at exact half-cent boundaries
- Repeated rounding and cumulative totals
- Very small exchange rates
- Large exchange rates
- Invalid zero or negative rates
- Extremely long decimal rates
- Integer overflow boundaries
- Currency changes during transaction editing
- Date changes affecting monthly reporting
- Sum of converted transaction values versus report totals
- No double conversion
- No currency symbol/decimal precision mismatch

Reports must aggregate the already-saved `amount_myr_minor` values, rather than reconverting the original foreign amounts using current exchange rates.

**Important:** For reporting, summing stored rounded transaction equivalents is the expected behavior. Recomputing a conversion on the total original amount can produce a different result and must not replace the saved transaction accounting values.

8. Confirm the app remains usable.

**A failed restore must never leave a partially restored database.**

| Severity | Definition |
|---|---|
| Critical (P0) | Financial data loss/corruption, incorrect balances, unsafe restore destroying existing data |
| High (P1) | Major feature broken, wrong conversion, persistent database integrity issue, serious security vulnerability |
| Medium (P2) | Important workflow failure, inconsistent state, incorrect filtering, significant UI usability problem |
| Low (P3) | Minor visual defect, polish, noncritical warning, small usability issue |

- Defect ID
- Severity
- Affected module
- Title
- Environment
- Preconditions
- Exact reproduction steps
- Expected behavior
- Actual behavior
- Source file and line reference
- Root cause, if established
- Evidence (test output, screenshot, logs, or query results)
- Recommended fix
- Regression test recommendation

Do not report hypothetical concerns as confirmed bugs. Label unverified concerns as Potential Risk or Needs Verification.

# 21. Release Acceptance Criteria

Do not recommend production release unless all of the following are satisfied:

- [ ] No unresolved Critical or High defects
- [ ] All implemented core CRUD operations verified
- [ ] Currency precision and conversion tests pass
- [ ] Exchange-rate snapshots preserved
- [ ] Financial report totals match stored MYR amounts
- [ ] No known database integrity violations
- [ ] Existing data survives supported migrations
- [ ] Backup export and restore verified
- [ ] Failed restore leaves existing data unchanged
- [ ] Application works offline
- [ ] Application state remains correct after restart
- [ ] Relevant automated tests pass
- [ ] Static analysis has no unexplained issues
- [ ] Android release build succeeds
- [ ] iOS release build succeeds where environment permits
- [ ] No known release-blocking privacy or security risks

If any critical acceptance test cannot be executed, clearly state that release readiness remains unverified for that area.

# 22. Execution Instructions

Follow this sequence:

**Step 1 — Discovery**

Inspect the project and map actual implementation against requirements.

**Step 2 — Static Analysis**

Run project validation commands and review architecture, financial logic, database code, and error handling.

**Step 3 — Automated Tests**

Run existing tests. Create and execute isolated additional tests where appropriate.

**Step 4 — Functional Validation**

Validate real application workflows using available devices, emulators, or integration tooling.

**Step 5 — Financial Validation**

Execute every defined monetary and exchange-rate test using deterministic fixtures.

**Step 6 — Data Integrity Validation**

Test persistence, database constraints, migrations, and failure recovery.

**Step 7 — Backup and Restore Validation**

Test valid, invalid, incomplete, corrupted, and incompatible backups without risking real user data.

**Step 8 — Offline, Security, and Platform Validation**

Check network independence, storage, privacy, lifecycle behavior, and platform compatibility.

**Step 9 — Final Report**

Provide the complete structured QA report, including execution evidence and exact source references.

## Final Rules

- Be rigorous, evidence-driven, and specific.
- Never fabricate test executions or results.
- Do not treat successful compilation as proof of correct behavior.
- Do not silently skip unavailable tests.
- Do not modify real user financial data.
- Do not automatically change production code.
- Never silently replace expected behavior with what the current implementation happens to do.
- Explain every functional deviation from the specification.
- Prioritize financial accuracy and prevention of data loss above cosmetic quality.
- Prefer reproducible automated tests over subjective assessments.
- If project access is unavailable, clearly state that execution is blocked and provide an executable test plan instead of claiming the application was validated.

**Begin immediately by inspecting the actual project and establishing its implemented feature baseline. Then execute the QA workflow and provide a detailed, evidence-based report.**
